# Key Issuance Automation

This document separates provider key lifecycle steps by how far banto can
automate them without exposing secret values to agents.

## Automation Lanes

| Lane | Meaning | banto command |
|---|---|---|
| Provider API | Provider exposes an API that returns a new one-time secret value | provider-specific `banto sync ...` command |
| Browser recipe | Provider only exposes a console flow | `banto sync browser-issue ... --recipe ...` |
| Browser record/reissue/revoke | Provider console flow must be learned first | `banto sync browser-record ...`, then `browser-issue --exposure-manifest ...` |
| Browser batch | Multiple console-only keys need the same closed-loop run | `banto sync browser-batch <plan.json>` |
| Existing Keychain import | A usable credential already exists under another local Keychain service | `banto sync import-keychain ... --from-service ...` |
| Propagate only | Replacement value is obtained by another trusted local command | `banto sync propagate ... --from-cli ...` |
| Manual cutover | Runtime behavior changes and needs rollout coordination | dedicated runbook |

## Current Provider Notes

- Cloudflare Account API tokens can be created through the Cloudflare API when
  a bootstrap token with `Account API Tokens Write` exists.
- Stripe normal secret and restricted keys are created or rotated in the
  Dashboard and may require a verification code.
- Stripe webhook signing secrets can be generated by creating a new webhook
  endpoint through the Stripe API. This is still a cutover because the endpoint
  URL and enabled events must match the application rollout.
- Anthropic Admin API supports API-key inventory and status updates. Runtime
  API key issuance still needs console or browser-recipe handling unless a
  create endpoint is available in the account.
- xAI runtime keys can use `banto sync xai-api-key` when an xAI management key
  is already stored as `xai-management`.
- The first management/bootstrap credential for each provider is intentionally
  outside full automation unless the provider offers a higher-level managed
  identity flow.

## Cloudflare Account Token

Create a policy file without secret values:

```json
{
  "policies": [
    {
      "effect": "allow",
      "resources": {
        "com.cloudflare.api.account.<ACCOUNT_ID>": "*"
      },
      "permission_groups": [
        {"id": "<PERMISSION_GROUP_ID>", "name": "<PERMISSION_NAME>"}
      ]
    }
  ]
}
```

Dry-run:

```bash
banto sync cloudflare-account-token cloudflare-api-token \
  --account-id <ACCOUNT_ID> \
  --policy-file cloudflare-policy.json \
  --dry-run
```

Live run:

```bash
banto sync cloudflare-account-token cloudflare-api-token \
  --account-id <ACCOUNT_ID> \
  --policy-file cloudflare-policy.json \
  --revoke-token <OLD_TOKEN_ID> \
  --validate --smoke-preset provider-validate
```

The creator credential is resolved from `CLOUDFLARE_TOKEN_CREATOR_API_TOKEN`,
then Keychain account `cloudflare-token-creator`.

## Stripe Webhook Endpoint

Dry-run:

```bash
banto sync stripe-webhook-endpoint stripe-test-webhook \
  --source-secret stripe-test-secret \
  --url https://example.com/api/stripe/webhook \
  --event checkout.session.completed \
  --dry-run
```

Live run:

```bash
banto sync stripe-webhook-endpoint stripe-test-webhook \
  --source-secret stripe-test-secret \
  --url https://example.com/api/stripe/webhook \
  --event checkout.session.completed \
  --delete-previous-endpoint <OLD_ENDPOINT_ID>
```

The new signing secret is stored and synced without being printed. Coordinate
application cutover before deleting the old Stripe webhook endpoint; omit
`--delete-previous-endpoint` until the new endpoint is live.

## Dashboard-only Credentials

Some providers only support key creation and deletion in a management
dashboard: create a new key, copy the one-time value from a modal, update the
application, then delete the old key. banto models this as a browser recipe so
the issued value is captured inside the local process and never printed.

Record the dashboard flow once:

```bash
banto sync browser-record ekyc-api-key \
  --provider ekyc \
  --start-url https://<provider-dashboard>/admin/api-keys \
  --output recipes/ekyc-api-key.issue.json \
  --capture-selector '<selector-for-one-time-api-key>' \
  --metadata key_id='<selector-for-new-key-row-or-preview>'
```

Dry-run, then run, the closed-loop command:

```bash
banto sync browser-issue ekyc-api-key \
  --recipe recipes/ekyc-api-key.issue.json \
  --exposure-manifest recipes/ekyc-api-key.exposure.json \
  --validate --dry-run
```

Webhook signing secrets classify as `manual_cutover`; pass
`--allow-manual-cutover` explicitly when you have coordinated the cutover.
(The provider-specific `providerb-credential` wrapper was removed in 5.3.0.)
